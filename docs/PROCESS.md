# 从想法到上线：Vibe Coding 全过程

[返回项目首页](../README.md)

本记录依据项目对话、现有实现、测试记录与发布提交整理，**不是逐字聊天记录，也不是正式用户研究报告**。个人项目作者负责选择方向与验收，Codex 辅助实现；未进行有样本规模的用户访谈或增长实验。

## 1. 起点：不是再做一个四字母测试

最初目标是做一个偏娱乐、语言有辨识度、测完愿意分享的人格测试网站。进一步明确：人可能半 I 半 E，也会在不同场景呈现不同特征，不应被单一类型完全定义。

形成的定位是“MBTI 毒舌版 / 你，不止一种人格”。传播性是设计目标，而非已经被数据证明的成果。吐槽集中于日常习惯，首页移除了“人格运行正常吗”“毛病”等容易造成误解的表述；部分结果页仍有“体检/运行”拟人化用语，后续需继续统一审核。

## 2. 范围收敛：把第一版做完整

确定 32 道主测、每道 ABCD 四选一，以及 8 道隐藏面加测。消费、网络、旅行人格作为后续专题，当前只标记“即将开放”，不伪装成可用功能。

核心路径：

```text
角色墙与首页 → 32道主测 → 主测结果与人格卡
                              ├─ 保存图片 / 复制网站链接
                              └─ 自愿继续8道隐藏面 → 双面结果与更新后的卡片
```

后来明确“32 题完成就能分享”。隐藏面从必须经过的步骤变成可跳过的邀请，保留扩展体验，又不强迫用户继续作答。是否提升完成率，需要后续统计验证。

## 3. 视觉方向：从参考图到统一界面

人工确定 Neo-Brutalism：粗黑边框、硬阴影、奶油底色和高饱和配色；为 16 类人格配专属角色，统一用于首页和结果卡。

首页逐步加入悬停放大、SVG 装饰和角色墙。角色墙采用交错列漂移与透视，支持悬停暂停、按钮切换静态展示和减少动态效果。收到反馈后，将整个人格墙移到首页最上方，介绍与测试入口顺延。

这不是全程一次生成的界面：多次使用截图反馈检查标题换行、内容位置、按钮、移动端溢出和动画行为。

## 4. 从专业描述到可读的人格卡

结果卡从偏技术性的强弱描述，逐步调整为人格称号、生活化句子、角色图与三个标签。例如“全自动情绪客服”强调一种可识别的行为，而不宣称诊断。

生成方形和竖版 PNG，方便用户自己保存、截图或转发。网站链接只指向测试首页，个人结果不编码在链接中。提出“自动存到相册”后，确认网页无法保证跨浏览器直接写入相册；当前保留下载与长按保存，不虚报该能力已实现。

## 5. AI 协作不是免验收

| 环节 | 人工判断与输入 | AI 辅助工作 | 验收依据 |
| --- | --- | --- | --- |
| 定位 | 娱乐向、可分享、不被单一类型限定 | 细化页面与功能方案 | 文案是否表达定位 |
| 设计 | 指定风格、人物参考、区块位置 | 实现布局、SVG、角色墙 | 页面截图与交互反馈 |
| 功能 | 明确32题即可分享、加测自愿 | 组件、状态流转、图片生成 | 浏览器走完整流程 |
| 内容 | 指出题意错位、重复或不明确 | 重写题干与选项、保持评分方向 | 人工逐项确认＋测试 |
| 发布 | 决定暂不部署后端，选择GitHub | 静态构建、上传、Pages检查 | 公开网址实际访问 |
| 故障 | 提供真实手机白屏截图 | 检查响应、拆包、压缩、补充WebKit测试 | 本地证据与真实设备反馈分开记录 |

使用的方法是“小范围说明目标 → 形成可检查的修改 → 运行测试 → 看实际界面 → 决定下一步”，不是把生成的代码直接当完成品。

### 协作指令示例（方法总结，非逐字历史记录）

- “先明确本轮范围：只调整第4题，不改变评分和其他题目。”
- “把题干和四个选项放进同一个明确场景，并检查与同维度其他题是否重复。”
- “生成代码后验证题目、得分方向、手机宽度和公开链接；不要把构建成功当作上线成功。”
- “只发布静态成品，不上传后端凭证、原始答题数据或本地工作资料。”

## 6. 发布取舍：从完整工程到静态网站

开发阶段使用 React + Next.js，并探索分享记录后端。由于用户决定先不做后端上线，另建 Vite 静态入口，复用问卷、评分和结果组件，替换依赖服务端的导航与分享能力。

GitHub 仓库只上传可运行成品。此选择降低了部署复杂度，但也意味着：不能提供持久化的个人结果链接、跨设备同步和服务端漏斗分析。技术细节见 [架构说明](ARCHITECTURE.md)。

## 7. 一次重要反例：单文件可打开，不代表手机可用

第一版把 JavaScript、CSS 和16张人物图全部塞进 HTML，产物约8.24 MiB。桌面和手机尺寸模拟可以打开，但随后收到真实 iPhone 白屏反馈，Safari 也未能正常打开。

排查事实：标题和背景已出现；服务端能返回200；正文依赖脚本；入口文件很大。**不能据此断言唯一根因是体积**，也不能把Chromium手机尺寸模拟等同Safari兼容性验证。

处理：

1. 保留单文件作为离线产物，在线版拆成小HTML、独立脚本与图片。
2. 将16张人物图从约6.26 MB压缩到约0.63 MB，原始素材不覆盖。
3. 增加无需应用脚本即可显示的加载提示、慢加载提示、错误编号和重试入口。
4. 补测WebKit，检查脚本延迟/失败、图片失败、答题和导出。
5. 明确记录线上WebKit图片加载仍有不稳定，不把“能进入答题”写成所有手机已完全修复。

入口HTML降至2,183字节，是产物大小变化；**不是全站只有2KB，也不是加载速度提高99%**。独立脚本、样式与图片仍需要下载。

## 8. 题库迭代：从换措辞到换测量场景

第4题经历了以下过程：

| 版本 | 问题与反馈 | 决策 |
| --- | --- | --- |
| 陌生城市参加活动 | 题干像问出行，选项却在讲现场社交 | 对齐活动场景 |
| 没熟人的活动开场前 | 与行业自由交流题重合 | 换一个行为角度 |
| 分享开心的小事 | “发给”和“现场观众”混用线上线下 | 不继续模糊改写 |
| 好笑视频与线上分享 | 用户认为仍不贴切 | 放弃该方案，未上线 |
| 与熟人散步后的安静 | 明确关系、情境，排除赶时间与不愉快 | 人工确认后上线 |

最终题目：

> 和一个很熟的朋友一起散步，没有赶时间，也没发生不愉快。聊完一个话题后，两人安静下来，你通常会：

- A：挺享受这段安静，不说话也自在
- B：先安静走着，想到想说的再开口
- C：顺着路上看到的东西，接着聊几句
- D：很快又抛出新话题，边走边聊才过瘾

保留该题原有E/I权重，增加内容检查并在公开页面答到第4题，确认四个选项及下一题跳转。规则测试只能保证实现一致，不能证明心理测量有效性。

## 9. 学到的东西

- AI 能加速从需求到可运行页面，但无法代替产品语义和题目质量判断。
- 先定义验收边界，才知道“能跑”“已发布”“手机可用”分别需要什么证据。
- 展示效果、传播目标和真实增长是三件事，项目成果说明应明确区分。
- 当前优先级仍是设备兼容性与题库质量；继续堆功能不能弥补这两个基础问题。
